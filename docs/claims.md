# Product positioning and evidence

## Position

**UI Foundry gives a coding agent the design-lead role for independent developers and small teams without a dedicated designer.**

Starting from an idea or an existing UI, it provides concrete visual recipes, original CSS and a runnable reference, routes implementation through compatible components, then requires actual rendering, task inspection and repair. The user supplies product intent and important constraints, not a specification for every control.

Positioning for users: **Let your coding agent act as a product designer—from the brief to a runnable interface, with design decisions, interaction implementation and review.** This is a beta design toolkit for a coding agent, not a hosted application builder. Outcomes depend on the model, tools and project; actual product quality requires project-specific verification.

The intended experience is idea-to-usable-product: the agent owns the design choices, integration and verification. “Ready to use” requires a working primary flow with real state, persistence where needed and recovery from failure. An installed sample or a library list alone does not meet that promise. External accounts, hosting and production services still use the target project's actual configuration and authorization.

Primary use: building or improving an interface with a coding agent. Secondary use: a complete portable design brief or a targeted design-workflow repair. It is a small portable design toolkit and workflow, not a hosted app builder or a replacement for mature component libraries, user research or project-specific design.

中文定位：**给没有专职设计师的独立开发者和小团队，让编程 Agent 兼任设计负责人。** 从一句需求或现有页面出发，用具体底稿、交互模式和组件适配替用户完成视觉与交互设计，减少无效工作，保留已有能力，再以真实任务验收。

## Claim register

| Claim | Required evidence | Current limit |
| --- | --- | --- |
| Self-contained design workflow | Public instructions and references install together, no private profile needed | Tools/model remain supplied by the user's agent |
| Ready-to-use delivery | A runnable product flow, connected data, preserved state, observed failure recovery and platform-appropriate controls | A goal of each implementation; the packaged samples do not certify arbitrary generated products |
| Supports several installation targets | Real file placement and package comparison | Not proof of runtime triggering or identical results in each client |
| Helps preserve existing behavior | Stored-data/task regressions on generated outputs | Per-case observations, not a universal guarantee |
| Reduces avoidable user work | Paired task completion, repeated-input and context-switch observations | Count the user's work, not just buttons or words |
| Produces better visual results | Same-content, same-viewport, anonymized comparative reviews; ultimately human evaluation | Independent AI review alone is limited evidence |
| Improves reliably | Multiple held-out tasks, repeated runs, multiple environments, failures disclosed | A single pilot cannot support this claim |
| Automatically repairs failures | Preserved failure → diagnosed responsible layer → revised artifact/skill → original and counterexample retest | Within current authorization; no unattended global updates |
| Checker validates review records | Malformed/valid-input tests | Never validates beauty, truth of evidence or product quality |

See [benchmark protocol and results](../benchmarks/README.md). Do not turn a tied result, a supplied illustration or successful package tests into a design-improvement claim. Do not advertise “perfect UI”, percentage improvements, reduced cost or speed unless an appropriate measurement supports that exact statement.
