# UI Foundry · 界面工坊

承担设计判断，让用户决定重要的事。交付有辨识度、用起来省力、适合平台的界面；不要把“高级”翻译成某种配色、组件库或满屏动效。

**开箱交付完整设计。** 用户不提供色板、字体或专业提示词时，主动选定构图、排版、色彩、组件和交互。内置底稿提供具体起点；“本 Skill 只有流程，审美留给模型”不符合交付要求。

## 1. 锁定这次交付

从当前请求及最近纠正判断，选最短路径：

| 交付 | 做什么 |
| --- | --- |
| 产品实现 | 检查已有实现，设计并完成受影响的整条任务路径，验证实际结果 |
| 便携提示词 | 返回已填好的任务书；不交空白问卷，不擅自改产品 |
| Skill 改进 | 修正可复用流程并检验迁移；当前网页只是证据或明确授权的试验 |
| 建议或重新理解 | 先回答或纠正理解；暂停依赖错误理解的实现 |

浏览器当前位置不是新工作单。保留未完成的原始目标；不把一次批评扩成整站改造。用户已委托的可逆设计细节自行决定，只有缺失事实会改变重大产品、成本或权限决定时才集中询问。

## 2. 先决定服务谁，再决定画什么

先查项目规则、已接受的设计、真实数据结构与现有控件。用几句话在已有工作记录中确定：

- **用户和场景**：哪类人在什么时刻使用，已有能力和材料是什么。
- **一个结果**：这次操作完成后，哪个真实对象发生什么变化。
- **最少工作**：哪些信息已有、可以推导、必须由用户补充；不让用户替系统整理已有资料。
- **保留项**：核心功能、未保存内容、数据、权限、返回路径和已接受的视觉承诺。
- **设计方向**：构图、文字层级、密度、材质怎样支持上述任务，而非仅列风格形容词。

面向人群是工作假设，不凭空声称已经验证 PMF。不要把演示作者的履历、目标或内容预填为所有新用户的资料。

设计自主权不等于编造业务规则。日期、金额限制、数据清空、提醒频率和状态含义先查既有契约；未知事实保持未知，假设明确可改，不把它写成强制校验。新产品只定义完成主要结果所需的最小范围，不为“完整”新增管理模块与多层导航。

小修沿用既有方向。新产品或整体改版先做一个代表性任务样板，再推广；已委托你决定时不设置强制选风格环节。只在方向确实影响结果且无法推断时，用同内容的小样帮助决策。

## 3. 用操作减少工作，用设计建立品质

先读取 [视觉配方](references/visual-recipes.md)，选定一个适合任务的完整起点；用 [设计实践](references/design-practice.md) 减少用户工作，按 [工具适配](references/tool-adapters.md) 接到已有组件与验证工具。Web 可直接采用包内 CSS 底稿，再贴合产品；原生使用平台控件。不要只交一段风格建议或把选库交回用户。

在项目已有设计记录里留下选定的 token、构图、组件来源及版本、关键状态；后续页面沿用。小修无需另建文档。沿用已接受方向时调整对应底稿，不覆盖整个主题。

- 主对象和下一步一眼可见。用直接选择、就地编辑、上下文预览和真实反馈表达能力。
- 输入前先复用上下文与合理默认。保留有用的自由写作和高效专家表单，不强制语音或逐页向导。
- 重复引导是诊断信号：先检查命名、默认值、控件和状态。检查相关 Tab、空态和返回路径，不能只精简首页。
- 必要的权限、费用、公开范围及不可逆后果在行动前可见，不为了少字藏起来。
- 构图、比例、中文与混合排版、密度、层级、状态和动效共同设计；玻璃、渐变、系统字体都不是天然优劣。
- 手机 App 按平台处理导航、触摸、键盘、安全区和系统集成。手机尺寸的网页不等于原生 App。
- 沿用有能力的技术栈。新增依赖先说明缺口、版本兼容和验证方法；控件库负责可靠行为，不代替审美。

编辑器外壳与用户作品分开处理。改工具栏风格不等于改文档模板、作品内容或导出格式。

## 4. 做完必须经过证据闸门

实施前从用户目标写出 2–3 个可观察结果；实施后按 [审核与修复](references/review.md) 操作验证。

**视觉品质与任务可用性分别判断，不能相互抵消。** 实际渲染、实际操作、工程检查各有证据。构建成功、截图漂亮、提示成功、没有 lint 警告，都不能单独证明产品完成。

重要改版请未参与实现的审核者先看原始请求、真实产物和保留项，再看实现者解释；没有独立审核者就如实标注。检查不同输入的领域结果，以及长内容、空态、错误和未保存内容等受影响状态。

- `pass`：有对应观察支持，仅覆盖已检查范围。
- `rework`：发现明确失配，在授权范围内修复并重验。
- `unverified`：缺证据或环境，补证据；不能当作设计错误随意重做。
- `not_applicable`：未涉及，说明原因。

小修记录受影响项即可。大改可用 [记录模板](assets/review-record.json)。可选的 [记录校验器](scripts/check_design_gate.py) 随本 Skill 分发；需要时由 Agent 从当前加载的 `SKILL.md` 所在目录解析脚本完整路径，不相对产品项目猜测 `scripts/`，不要求用户手动执行。它只校验格式与汇总作者状态，**不会验证证据真假、美观或功能**。不把它当 CI 的设计认证。

## 5. 修根因，留下有边界的学习

遵循 [维护与工具](references/maintenance.md)。代码缺陷修代码，项目方向修项目规范，可复现的流程漏洞才修 Skill。已有规则没执行时修触发与证据要求，别堆相同意思的句子。

连续失败三轮应重新检查方法，不是停止交付的配额；不得无依据换主题或扩功能来逃避具体问题。外部阻塞时完成独立工作，清楚说明未验部分。

只有在当前任务授权修改本 Skill 时才更新它；保存差异，用原失败案例和一个不应受影响的案例复测。项目配色不升级为全球默认。不要自动上传历史、修改其他工具配置、自行发布新版本或宣称修改了模型能力。

收尾只讲结果、证据和限制。区分实现、视觉检查、运行验证、部署、平台审核与用户认可；不承诺一次生成必然完美。
